# SUGGESTIONS — 2026-11-07

### [2026-11-08T00:30:00Z] feat/ssh-task-dispatch
- What changed: added federated task dispatch (v0.18.0) — `src/tasks.rs` durable store with addressable targets and lease-based claims, `/api/v1/tasks*` routes with per-device ownership, four MCP tools (`task_dispatch`/`task_claim`/`task_report`/`task_status`), a dashboard TASKS card, and `wtf tasks`. Two bridge defects found and fixed by the live smoke test (2xx decode, error-body surfacing). Skill doc corrected (wrong port, non-existent fallback).
- Next step: add a worker polling loop so a paired machine claims designated work without a human asking, then replicate the task board across federated hubs the way events already replicate.
- Adversarial/security: 1. A `target` selector is attacker-influenced input from a peer device — `valid_target` fails closed on unknown prefixes, which is the right shape; keep it that way rather than accepting arbitrary strings. 2. `task_claim` returns the full `detail`, so any enrolled device that can guess a selector can read another team's task text; if tasks ever carry sensitive instructions, keep them in the bound encrypted chat and leave only a pointer in `detail`.
- Privacy/data lifecycle: task records persist in `tasks.json` indefinitely and hold work descriptions and results — add a retention/prune pass (`MAX_TASKS` caps volume but never ages entries out), and treat `detail`/`result` as operator-readable only.
- Supply-chain/third-party risk: still zero external crates after this change, and the new module adds none. The task record carries no new dependency surface at all.
- Systems-architecture/devops: the lease model is the right call over hard locks, but 900 s with no renewal until the first `running` heartbeat means a long pre-work phase can lose the claim; consider having `task_claim` itself return the lease deadline so a worker knows when to heartbeat.
- Reliability/verification: the two defects this change shipped with were both found by running the real binary, not by reading it — the e2e test now pins the loop and the ownership guards, so keep extending that test rather than adding unit tests for the happy path.
- Governance/sovereignty: capability-gated `wtf tasks` means the operator can audit designated cross-machine work from any machine; that is the accountability surface for delegated action, so it should stay readable without an agent's cooperation.
- Terminal-orchestration/SWE-bench: dispatching over the task lane is honest benchmarking input — the record captures the instruction and the result verbatim, which is exactly the pairing a SWE-bench-style harness needs.
- Master-orchestrator/self-prompting: the pull model makes orchestration failure visible instead of silent — a task resting `queued` says "nobody is listening," which is better than a spawn that fails into a log. Prefer that diagnosability over convenience.
- Developer-experience/ergonomics: the worker path prints the instructions and the exact `task_report` call to make, which is the right ergonomics; the dispatcher path still requires the agent to remember `task_status {task}` to collect, so consider making the dispatch reply state the check-in cadence it expects.

### [2026-11-08T01:35:00Z] feat/runner-orca-herdr
- What changed: v0.19.0 agent runners — `src/runner.rs` resolves Orca (supervised) then Herdr (durable terminal), builds and unit-tests the argv, launches under a wall-clock cap, and records the handle; `task_run` + `runner_probe` MCP tools, `GET /tasks/runners`, `POST /tasks/{id}/run`. Three real defects found by driving the actual Orca binary: nonce double-consumption (401), the mandatory `--agent`, and a launch outliving the client read timeout.
- Next step: redeem one remote pairing on the mac (Orca environment or Herdr machine) and prove one dispatch → claim → task_run → task_report cycle against it; everything but the transport is already proven locally.
- Adversarial/security: a task's `detail` becomes an agent prompt on another machine, which is the highest-leverage input in this system — an enrolled peer can currently address a spec at any target it can match. The claim gate is the only thing between a hostile peer and arbitrary agent execution, so consider scoping `task_run` to device-allowlisted targets before this reaches an untrusted network.
- Privacy/data lifecycle: the launched agent receives the full task detail as its prompt, and runner stdout is stored in `run_handle`/`detail` — neither is redacted. Anything an agent prints on startup lands on an operator-readable board.
- Supply-chain/third-party risk: the runner shells out to `orca`/`herdr` by name from PATH, so PATH is now part of the trust boundary. `which` rejects path-like names, but a hijacked PATH entry would be executed; pin the resolved absolute binary (already done) and consider refusing relative or world-writable locations.
- Systems-architecture/devops: `DEFAULT_ORCA_AGENT = "codex"` is a real deployment assumption, not a neutral default — on a machine without Codex, Orca will fail at launch. Make the default configurable per machine rather than per call.
- Reliability/verification: the fake-runtime e2e is the right shape — it pins the argv contract without needing a second machine — but it cannot catch runtime-version drift. Add a `runner_probe --deep` that runs the real `--help` and reports whether the flags we build are still accepted.
- Governance/sovereignty: starting an agent on another person's machine is an authority decision, and today it is authorized by any enrolled device that can claim a task. Record who launched what, on which machine, in the event feed (partially done) and make that the auditable answer to "who ran this."
- Terminal-orchestration/SWE-bench: Orca's supervised workers already report through a Run, so the next real win is importing `worker_done` back into the task result automatically instead of requiring the agent to call `task_report` itself.
- Master-orchestrator/self-prompting: the design now has two ways to start work (hub-launched runner vs. an agent that claims and runs itself). That is one too many unless documented as "runner for unattended targets, self-claim for attended ones" — otherwise future contributors will not know which is canonical.
- Developer-experience/ergonomics: `agent-hooks-review-prompt` is an opaque failure for a first-time user; the skill documents it, but the runner could detect that specific string and print the fix inline instead of making the reader look it up.
